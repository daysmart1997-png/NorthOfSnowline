## 房屋优化后的执行批次

当前人物自带动作 v3 与两屋差异化模型已接入 Mac。最终 21 组检查、原生室内操作和两条完整往返已通过；本轮将连同流程 1–4 一起同步 GitHub，Windows 尚未复验。用户现已授权做到顺序 4 并上传 GitHub，阶段交付见 31_CHAPTER_FLOW_RELEASE.md；以下保留各批验收范围，玩家试玩暂停。

1. **收尾验收当前版本。** 用正常新游戏完成出门准备、去维修间、修模块、返程求援，并检查新家具下的可选线索、旧存档恢复和补救入口。保留直达/避风两条路线的记录，区分实际游玩与测试重定位。先解决阻断问题；由用户要求同步时，再将源文件、GLB、导入设置和代码一起提交/推送，Windows 拉取 LFS 后独立复验。
2. **先做小范围探索交互样板。** 第一批建议只做一处可搜寻家具和一处非文字环境线索，例如维修间零件柜提供数量受控的维修物资，小屋的生活痕迹提示某人匆忙离开。先写清玩家如何发现、回报如何影响准备、错过能否继续，再接模型/动画/音效。搜过状态须保存，重复读档不能刷物资，不能给全部装饰都加高亮；户外两处探索样板沿用上表第二阶段逐步扩展。
3. **将探索结果接到求生选择。** 在既有铁路直达线和避风线中检查时间、暴露、补给和绕路价值；让观察到的线索帮助玩家选择添柴休息、补水或尽早返程。补救途径必须可发现，调参依据实玩记录，不直接增加掉血速度或强制暴风雪制造紧张。
4. **打磨人物回应和声音层次。** 优先一段求援回应与一段人物遗留信息，配合室外风、门内阻隔、炉火和危险提示的混音。保留字幕和重读，区分本章求援完成与寻找周岑的后续悬念；人声素材尚未准备时先完成文本、触发和音量层次。
5. **首次玩家测试后再平衡。** 3–5 位未熟悉项目的人独立玩，记录首个目标、第一次水/火/休息、误解和放弃点；按具体卡点调整引导、消耗和回报。此步骤需要真实参与者，自动化检查不能代替；不默认联系他人或录屏。
6. **双平台候选版，然后第二章短样板。** 检查两端导出启动、完整 LFS、中文与大字、音量/输入、存档恢复、主线/可选分支和帧耗时。第一章验收后再制作北坡入口、一个新困难和一处证据，不直接扩成大地图。

每一批固定采用：**明确玩家体验与验收条件 → 小范围实现 → 碰撞/交互/状态/存档联调 → 对应自动检查与原生实玩 → 更新 PROGRESS → 按用户要求同步 GitHub**。玩法状态继续由 expedition.gd 等现有状态层维护，家具和 UI 不另建背包数据。一次只验收一个可体验的批次；跨设备不同时修改同一个 Blender/GLB。
